# 本地精华移植施工单

状态：已立项，按 M0 → M1 → M2 → M3 严格串行

产品主干：`origin/main`（立项基线 `8d6b0ca`，十关战役 + 潜行系统）

只读来源：`origin/local-polish-line`（P0–P4 工程质量 + A1/A2 角色资产）

施工分支：`codex/remote-trunk-port`

## 0. 目标与裁决原则

以远端产品线为唯一玩法主干，把本地打磨线中已经验收的角色资产、资产
管线和渲染工程能力按需移植过去。两条线从初始化后完全分叉，本施工单是
唯一跨线施工锚点；除本文件外，不迁移两线既有 docs 历史。

当预设范围与 M0 实测冲突时，以 M0 证据为准。任何范围修正必须写入 M0
报告并等待复验者明确放行，不能在实现阶段自行扩大。

## 1. Git 拓扑纪律（最高优先级）

1. 全部施工只发生在从 `origin/main@8d6b0ca` 创建的
   `codex/remote-trunk-port`。
2. `origin/main` 与 `origin/local-polish-line` 均不可写，不在其上直接提交。
3. `origin/local-polish-line` 只作为文件级来源。需要取文件时仅使用：

   ```bash
   git checkout origin/local-polish-line -- <明确、逐项审过的具体文件路径>
   ```

4. 严禁 merge、rebase 或 cherry-pick 两条线的任何历史；严禁用目录级或
   仓库级 checkout 代替明确路径清单。
5. 严禁 force-push 任何分支。
6. 每阶段一个独立 commit、一个独立报告、一次独立复验。上一阶段未收货，
   下一阶段不得开始。
7. 提交前核对 staged path；用户已有改动、第三方子模块脏状态和阶段外文件
   一律不带入。

## 3. M0 审计：零代码改动

M0 报告必须回答以下问题，并给出可独立复算的命令、原始数据或运行截图。

### 3.1 角色现状

- 拆包 `public/models/characters/` 下 kid、villain、police 及其
  `-bootstrap` / `-lod1` 变体；逐文件记录字节、三角面、材质、贴图、skin、
  关节数、骨骼名称和动画 clip。
- 查明运行态色块小人的真实原因：当前加载的是 bootstrap 占位、LOD，还是
  正式 GLB 本身就是该造型。
- 定位角色加载、渲染、动画和状态映射的真实模块；不得仅凭文件名推断
  `chaser-fsm.ts` 或其他玩法模块承担渲染职责。

### 3.2 性能与体积基线

- 对现有约 47 MB 资产按角色、环境、纹理、音频和其他类别分解。
- 实测 draw calls、triangles 和首屏阻塞字节；若项目没有 QA 统计，报告必须
  写明浏览器/网络面板或 Three.js 统计的测法与采样状态。
- 查实 Meshopt、Draco、WebP、KTX2 的实际使用情况，区分“配置/依赖存在”与
  “生产资产实际采用”。
- 查明是否已有压缩、Validator、体积预算或质量门禁管线。

### 3.3 渲染现状

- 审计灯光、阴影、环境贴图、色调映射、纹理各向异性和阴影投射清单。
- 拆解 `quality.ts` 或实际替代模块的设备分档、质量开关和运行时降级策略。

### 3.4 M1–M3 差距矩阵

对 §4–§6 每个预设项标注：

- 远端已有：保留，并说明无需移植的证据；
- 远端缺失：列入候选范围；
- 两线冲突：解释冲突点、风险与推荐取舍；
- 审计修正：若预设不成立，给出新的范围提议，等待复验者裁决。

### 3.5 授权与追溯

- 从本地线 `art-source/Characters/**/Reports`、README、来源与许可证记录追溯
  三角色几何、纹理、动画的来源。
- 列出 M1 若移植时必须一并带入的报告/notice，确保最终 GLB 可追溯。
- 对地域、分发、署名或 notice 风险单列，不用“项目内已有”代替授权核对。

## 4. M1 角色资产移植（待 M0 修正）

1. 文件级移植本地线三个正式角色 GLB：21 关节共享骨骼、9 个内嵌 clip、
   Meshopt + WebP；其中 villain 使用 A2 返工的约 1.04 MB 单网格版本。
2. 接入远端现有角色渲染与状态机，替换色块角色，但不移植本地玩法 FSM、
   关卡或胜负逻辑。
3. 保留远端 bootstrap / LOD / 流式加载框架（若 M0 证实它确实存在且有效），
   新 GLB 作为正式档接入。
4. 补齐远端躲藏/蹲伏映射：优先从
   `art-source/_Shared/Animations/` 的骨骼源制作 Crouch / Hide clip 并走完整
   管线；若短期用 Idle / LookAround 代偿，必须明确标为临时方案。
5. 验收：远端既有 65 个测试不删不改且全绿；十关均可进入并可玩；三角色
   在桌面与 375 px 正式游戏相机下清晰可辨；跑、藏、被抓状态迁移有实拍与
   QA 数据；控制台零错误。

## 5. M2 资产压缩管线移植

1. 从本地线精确取用并适配 `tools/art_pipeline` 中必要的 gltfpack/Meshopt、
   WebP、stddev 门禁与官方 glTF Validator 能力，不整目录盲取。
2. 对远端当前全量资产跑可复现压缩；压缩前后同机位目视一致，十关主题均
   有抽样。
3. 以 M0 实测为基线记录总量与首屏阻塞字节。预设目标为总量至少减半；若
   达不到，报告实际数字、瓶颈和不牺牲画质的边界，不静默放宽。
4. 统一资产版本参数为单点定义，消除各模块各自写 cache suffix 的漂移。

## 6. M3 择优渲染优化移植

只移植 M0 证明远端缺失且收益成立的项目：

- 跟随式、纹素对齐的阴影相机；
- 迷宫/建筑阴影代理体；
- 贴图各向异性；
- RoomEnvironment + PMREM；
- 角色合批与关节化阴影代理；
- QA render 分类分解统计。

每项必须独立可回退，给出前后 draw calls、triangles、阴影面数和正式机位
截图。远端低多边形平涂美术基调保持不变；PBR 化不是 M3 目标。

## 7. 明确不移植

- 本地追逐 FSM、关卡、胜负与其他玩法层；
- 本地 WebAudio 合成音效，远端自适应配乐 stems 保持原方案；
- 两线既有 docs 历史；
- 任何仅因“本地已验收”但 M0 无法证明远端受益的实现。

## 8. 通用报告与验证规则

1. 每阶段逐条写“完成 / 跳过 + 原因”，并附可独立复算的数据、拆包结果、
   同机位截图和测试摘要，禁止只写布尔结论。
2. 远端现有测试不得删除或弱化；新增测试遵循远端现有结构和命名风格。
3. 每阶段提交前 `npm run lint`、`npm run build`、`npm test` 全绿；M0 若因
   零代码性质只运行基线，也要在报告中给出真实结果。
4. 浏览器证据必须来自远端产品线正式游戏相机；DCC 图只能证明资产细节，
   不能替代运行态验收。
5. 所有数字绑定 commit、资产 SHA 和采样场景；截图必须记录视口、相机或
   可复现 QA 状态。
6. 独立复验可能拆 GLB、重测性能、重拍截图和抽玩十关，报告不得使用
   “待浏览器验证”标记完成。
